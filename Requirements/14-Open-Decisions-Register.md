# Open Decisions Register

Every requirement in this set traces back to a specific board scenario. Where that scenario surfaced a genuine open question rather than a resolved design, it's tracked here rather than silently defaulted. This is the register a business stakeholder or product owner should work through before build — each item includes why it matters and, where the modeling process reached one, a recommended default (never treat a recommendation as a decision already made).

| ID | Context | Decision needed | Why it matters | Recommended default |
|---|---|---|---|---|
| DEC-001 | Authority Administration / Binding | Should a cell's authority grant reference which capacity provider(s) it derives from, if a cell can be backed by multiple providers with different limits? | May require modeling multiple concurrent authority grants per cell rather than a single number; also affects whether a bind's provider allocation needs to reference the specific authority grant that justified it. | Not resolved in the model — flagged as a real domain question, not defaulted. |
| DEC-002 | Authority Administration | Does underwriter authority validation need to account for an aggregate pool across all underwriters in a cell, or is each underwriter's limit independent? | Changes whether granting one underwriter authority can be blocked by others' existing grants. Real domain question, not a technicality. | Not resolved — confirm with governance stakeholders. |
| DEC-003 | Authority Administration | Is granting cell-level authority purely internal (TFP governance), or does it require the capacity provider's own sign-off? | Affects who the `GrantCellAuthorityLimit` actor legally is and what evidence the event needs to capture. | Not resolved. |
| DEC-004 | Authority Administration | When authority is revised mid-cycle, should in-flight submissions be grandfathered (evaluated against the old rule) or re-evaluated against the new rule? | Governance-critical: the whole point of authority limits is current risk appetite. Affects broker/underwriter relationship if re-litigated. | Re-evaluation, as the safer default for a governance-critical system — but the mechanism (FR-AA-009) is built to support either stance, recording which was applied. |
| DEC-005 | Authority Administration | Does revocation trigger a review flag on the underwriter's recently bound business? | A thematic-file-review-style pattern-detection question, similar to reopen-count tracking (DEC-020). | Not resolved. |
| DEC-006 | Submission Intake | Is `SubmissionNormalized` genuinely a separate async event from `BrokerSubmissionReceived`, or should they collapse if normalization is synchronous/fast? | Depends on actual ADEPT integration latency — an implementation detail with architectural consequences. | Depends on measured latency; not resolved. |
| DEC-007 | Submission Intake | Does a failed normalization get an automatic broker notification, or is chasing manual? | Silent failure risks brokers bypassing the platform entirely — a real adoption risk. | Not resolved — flagged as high-priority given adoption implications. |
| DEC-008 | Submission Intake | Is there a retry limit or timeout before a failed submission is considered abandoned? | Operational cleanliness; affects exception-queue volume over time. | Not resolved. |
| DEC-009 | Submission Intake | Is broker-authorization rejection a hard block or a soft "held for review," and does the broker get any feedback? | Silent disappearance is a worse broker-experience problem than a normalization failure — the broker won't know to chase it. | Not resolved — flagged as a real UX risk. |
| DEC-010 | Submission Intake | What's the actual duplicate-matching heuristic — exact-field or fuzzy/probabilistic? | Materially affects false-positive rate; needs a real answer, not a placeholder. | Not resolved. |
| DEC-011 | Submission Intake | Does a confirmed duplicate supersede the original submission ID, or spawn a version chain? | Affects event-stream integrity and downstream traceability. | Superseding via an explicit link (`SubmissionSuperseded`), preserving both records — not silent discard. |
| DEC-012 | Search & Retrieval | Should every search be logged, or only at query-level (not per-keystroke)? | Logging access to sensitive risk/pricing data has real audit value, but per-keystroke logging adds friction to a fast search UX. | Query-level logging. |
| DEC-013 | Search & Retrieval | Does free-text search cover normalized ADEPT fields only, or raw broker documents too? | The latter is a materially bigger document/full-text search problem, not a structured-field search extension. | Not resolved — scope-defining question. |
| DEC-014 | Search & Retrieval | Should a narrower "same named insured, cross-cell" flag be visible to underwriters without exposing full submission/pricing detail? | A possible middle ground between full cell-isolation and full cross-cell visibility. | Not resolved — proposed as worth exploring. |
| DEC-015 | Underwriting Decisioning | Does every modified-terms referral approval require underwriter acknowledgment, or only above some materiality threshold? | Affects process friction for minor referee adjustments vs. governance completeness. | Not resolved — currently modeled as always required. |
| DEC-016 | Binding | Does a renewal's new submission carry forward exposure/PML context from the expiring policy automatically? | Depends on Exposure Intelligence's exploratory status; the linkage should exist even before those contexts are built. | Not resolved — flagged for later. |
| DEC-017 | Binding | If renewal is initiated but the broker doesn't respond before original expiry, does coverage lapse or is there a grace/held-covered period? | A real contractual question with legal implications outside pure architecture. | Not resolved — requires underwriting stakeholder input. |
| DEC-018 | Bordereaux Settlement | Does a post-agreement adjustment need its own approval cycle, or ride along in the next period's normal agreement process? | Affects process overhead for small corrections vs. governance rigor for large ones. | Ride along by default, unless a materiality threshold is defined for separate sign-off. |
| DEC-019 | Claims | Could quota share change post-bind (novation, reinsurance restructure), requiring point-in-time versioning rather than a simple lookup? | Parallel to DEC-001 — affects whether claim payment allocation is a simple lookup or needs Context-0-style versioning. | Not resolved. |
| DEC-020 | Claims | Should there be a limit on claim reopen count, or escalation/pattern-detection if it reopens repeatedly? | A natural extension of the audit/pattern-detection theme running through the model; not essential for initial build. | Not essential day one — flagged as a future extension. |
| DEC-021 | Exposure Intelligence / External Threat | Should geocode precision be a grid/hex-bucket aggregation rather than exact coordinates? | Exact coordinates risk false precision; grid/hex is standard cat-modeling practice and keeps aggregation queries performant. | Grid/hex-bucket aggregation. |
| DEC-022 | Exposure Intelligence / External Threat | Who owns the concentration/PML threshold, and does it vary by season or current reinsurance program? | Domain-expert-owned parameter; the system enforces it, doesn't define it — but where it's configured and by whom needs to be decided. | Not resolved — same pattern as Context 0's authority rules. |
| DEC-023 | Exposure Intelligence | Is exposure removed effective the cancellation date, or immediately regardless of effective date (future-dated cancellation)? | Mirrors the bind-time-vs-settlement-time gap in Bordereaux Settlement — "as-of-today" and "at-any-future-date" exposure are genuinely different questions. | Not resolved — may require the projection to be date-aware rather than a single running total. |
| DEC-024 | Portfolio Governance | Is a freeze automatic on threshold breach, or does it require human sign-off? | Automatic freezing is operationally powerful but risky — a bad data feed or model glitch could halt live business unnecessarily. | Automatic alert + recommended freeze + human confirmation, at least until there's a track record — a risk-appetite decision for TFP stakeholders, not a silent default. |
| DEC-025 | Portfolio Governance | Does a submission blocked by a freeze auto-resume once the freeze lifts, or require active resubmission? | Terms/pricing may have moved on during the freeze period. | Auto-resume with a re-validation step. |
| DEC-026 | Portfolio Governance | Is freeze-override authority configurable/versioned like Context 0's authority model, or a small fixed list? | Given the risk-appetite significance of an override, likely a very short, tightly controlled list rather than broadly delegatable. | Small fixed list (e.g. CUO only) — not resolved definitively. |
| DEC-027 | Portfolio Governance | Should a freeze override require dual sign-off (four-eyes)? | This is the kind of single-point-of-override-with-no-check that shows up in an internal audit finding. | Worth taking seriously given this overrides a risk control triggered by external data — field is built to support it (`coSignedBy`) regardless of whether it's made mandatory. |
| DEC-028 | Capital & Reinsurance Instruments | For an index-triggered cat bond, does index-crossing self-execute the trigger, or does it require external determination (bond calculation agent)? | Same "don't silently auto-decide a money-moving event" concern as claim-period validation (NFR-003). | Not resolved. |
| DEC-029 | Cross-cutting | Should reference-field names (e.g. `NotifyClaim.policyReference`, `RaisePriorPeriodAdjustment.originalBordereauId`) be aligned to match their source `idAttribute` field names (`PolicyBound.policyId`, `BordereauDrafted.bordereauId`) exactly? | Found during the Step 8 completeness check (`15-Completeness-Check.md`) — the data is traceable by convention but not by exact name, which would fail a strict automated check. | Align names if the model is regenerated; cosmetic, not urgent. |
| DEC-030 | Cross-cutting | Should a cross-context compliance/audit dashboard read model be built to query audit-flag fields (`freezeCheckPassed`, `validatedAgainstBindTerms`, `hasImpact`, etc.) in aggregate, or is per-event audit data sufficient? | Found during the Step 8 completeness check — each audit flag is captured correctly per-event, but nothing currently lets someone query "show every decision where X audit check failed/didn't run" across many records. | Not resolved — lower priority than GAP-001/GAP-002 since the underlying facts are at least recorded. |
| DEC-031 | Solution Architecture | Managed Postgres (matching TFP's existing cloud/on-prem platform) vs. self-hosted CloudNativePG in-cluster? | Real financial transaction data — backup/PITR/compliance posture should match whatever TFP already standardizes on, not be reinvented per project (`Solution Arch/03-solution-architecture.md` ADR-013). | Prefer managed if TFP has one available; not resolved. |
| DEC-032 | Solution Architecture | Identity provider for a mixed internal-staff (underwriter, governance, ops) + external-party (broker, capacity provider/TPA) access shape — one enterprise IdP with external guest accounts, or a B2B2C-style split? | Materially different identity shape than a typical consumer or pure-internal app (ADR-010). | Depends on TFP's existing infrastructure; not resolved. |
| DEC-033 | Solution Architecture | Secrets management platform (Vault, cloud KMS, or equivalent)? | An enterprise underwriting platform shouldn't be the first place secrets policy gets decided (ADR-018). | Deferred to the organization's existing platform; not resolved. |
| DEC-034 | Solution Architecture | Data privacy/protection classification for submission and claim data (named insureds, loss details) across TFP's operating territories (Bermuda, LatAm, APAC per `bordereaux.md`)? | Needs compliance input, not an architectural default. | Not resolved. |

## Using this register

Each row should be assigned an owner and closed out (with the decision and rationale recorded) before the corresponding functional requirement is finalized for build. Rows with no recommended default are genuinely open — do not proceed to implementation assuming a specific answer.
